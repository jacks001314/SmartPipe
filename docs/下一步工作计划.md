## 1. 先验证的前提

开始改造前先确认三件事，任何一项不成立都会影响路线：

1. `pipeline-lead` 在 Syntropy 中能看到 Agent 管理工具，能创建子 Agent，并通过 A2A `request/response` 派活。
2. GitHub 私有仓库可以配置 GitHub App 和 Webhook，具备 Issue、评论、标签、PR 和元数据权限。
3. lead 有一个干净的本地/自托管工作区，能检出仓库、应用 patch 并运行目标项目的构建和测试命令。

当前运行时的 GitHub 插件 MCP 握手超时，正式接入前需要恢复连接或直接配置 GitHub App。第一项如果没有平台权限，降级为固定角色模板 + A2A，不阻塞入口闭环。

## 2. 第 0 周：集中配置管理台、项目注册与运行时管理

目标：管理员能在界面上配置项目、GitHub 地址和凭据，Agent 不接触 token。

任务：

- 实现 `projects` 注册表：项目名、GitHub provider、仓库地址、默认分支、Issue 仓库、标签前缀、审批人/CODEOWNERS、验证契约路径、发版配置、蓝信群绑定。
- 实现凭据管理：GitHub App、Webhook secret、蓝信 App ID/Secret/API Base、Syntropy Master URL/service token、Git 凭据；AES-GCM/KMS 加密，界面只显示掩码。
- 实现连接测试：GitHub 仓库读取、蓝信 token、Syntropy 可达性、Git 只读 clone。
- 实现项目解析：蓝信群/会话 → 项目；GitHub installation + repo → 项目；找不到时拒绝或转人工。
- 配置 Agent 工具权限：lead 拥有蓝信/GitHub 通信工具；dev/test/release 默认没有外部通信工具。
- 审计配置变更，禁止在日志和响应中输出明文凭据。

验收：

- 管理员能新增项目并测试 GitHub/蓝信/Syntropy 连接。
- 轮换凭据后旧值立即失效，新任务使用新值。
- Agent 任务消息中不出现 token；子 Agent 没有 GitHub/蓝信通信权限。
- 详细字段见 [集中配置管理台设计.md](集中配置管理台设计.md)。

同一阶段补齐 Syntropy 运行时管理：

- 新增 Runtime Manager 服务，按源码核对后的三层边界实现：进程管理器启动和守护 `syntropy-app-server`；Go SDK 部署 Master 和 Worker；HTTP adapter 调 `/api/agents`、`/api/agent-templates` 创建 pipeline-lead 并同步模板。
- Go SDK 只是 App Server 的客户端（`Options.BaseURL` 默认 `http://127.0.0.1:8765`）。启动顺序固定为：拉起进程 → 健康检查/handshake → 再创建 SDK Client。
- 当前 Go SDK 没有 Agents / AgentTemplates 分组，先在 Runtime Manager 内封装 HTTP adapter，不改 Syntropy 源码；后续上游补齐再切换。
- 配置管理台增加“Syntropy 运行时”页面：集群拓扑、App Server、节点、lead 实例和生命周期操作。
- 长操作返回 `operation_id`，页面轮询/订阅；重复点击幂等，停止/删除二次确认。
- 节点注册使用一次性 join token；service token 和 join token 不进入浏览器存储，注册命令只展示一次。
- 运行时操作全部写审计日志；Master/Worker 移除前检查活跃任务并先 drain。

运行时验收：

- 能在界面启动 App Server 进程，并用 SDK 部署 Master 和 Worker，看到节点心跳。
- 能创建 pipeline-lead，绑定项目、模板和 Worker，实例进入 running。
- 有活跃任务的 Master 不能直接停止/移除。
- 非管理员不能调用运行时 API，页面不显示 token 明文。
- 具体页面/API 见 [Syntropy运行时管理设计.md](Syntropy运行时管理设计.md)。

## 3. 第 1 周：蓝信到 GitHub Issue 的闭环

目标：每条有效反馈对应一个可追踪的 GitHub Issue，lead 能回复用户。

任务：

- 保留 `backend/cmd/bot`，补齐消息去重、用户标识、附件元数据和任务创建。
- 新增桥接表：`source_message_id`、`chat_id`、`lanxin_user_id`、`github_repo`、`github_issue_number`、`syntropy_task_id`。
- 配置 GitHub App/Webhook；实现创建 Issue、写评论、加标签。
- 创建 `pipeline-lead` 角色，注入 GitHub、蓝信和 Syntropy 管理工具；lead 是唯一对外通信接口。
- lead 自己完成分诊、重复检索、建单和回复；不派生 Agent。我们的桥接代码不调用 Agent 创建接口，子 Agent 由 lead 自己创建。
- 将 `orchestrator` 收敛为任务网关/桥接服务，不再承担完整业务状态机。
- 不再把 `issue-service` 作为独立 Issue 系统；复用它已有的持久化能力或替换为最小桥接存储。

验收：

- 20 个样例中归档准确率 ≥ 90%。
- 同一 `platform_message_id` 重复投递只建一个 Issue。
- 每个 Issue 都能从蓝信消息追踪到 GitHub Issue 和 lead 任务。
- 不依赖 GitHub Actions。

## 4. 第 2 周：dev 开发与 lead 最终合并

目标：一个真实 Bug 完成 Issue → dev → patch → lead 验证 → 合并。

任务：

- 新增 dev 角色模板；由 lead 自己创建并派生，子 Agent 只读仓库，不能调用 GitHub/蓝信通信工具。
- dev 在独立工作区复现、修改、写单测，跑 build/lint/unit，回传 `base_commit + patch + 日志 + 环境`。
- 仓库增加 `smartpipe.yaml` 或 `Makefile`，固定 `build`、`lint`、`unit`、`integration` 命令和工具链版本。
- lead 在干净副本应用 patch，执行 required 命令，检查敏感文件和 diff 大小。
- lead 通过后在 `agent/<issue-number>` 分支生成提交并合并主分支；只有 lead 有写权限。
- 保存验证报告：patch hash、命令退出码、耗时、工具链版本、执行人和时间。

验收：

- 1 个真实 Bug 完成端到端修复和合并。
- dev 自测通过但干净副本失败时，lead 阻断合并并退回 dev。
- 第 3 轮仍失败时 Issue 进入 `blocked`。
- 主分支不能由 dev/test 直接推送。

## 5. 第 3 周：复杂 Issue 审批与独立测试

目标：复杂任务未经 GitHub 确认不能进入开发；测试有独立证据。

任务：

- 实现复杂度判断和 `discussing` / `awaiting_approval` / `approved` 状态。
- GitHub Issue 评论区支持 `/plan`、`/changes`、`/hold`、`/reject`、`/approve vN`。
- 服务端校验评论人仓库权限、CODEOWNERS、方案版本和内容哈希；方案变更后旧批准失效。
- dev 派生工具检查 `approved` 状态，未批准直接返回 `approval_required`。
- 可选 test 子 Agent：干净副本应用 patch，跑集成/回归测试并回传报告。
- 蓝信同步讨论摘要和最终决策，转述评论不能作为批准。

验收：

- 复杂 Issue 未审批时无法派生 dev。
- 无权限用户的 `/approve` 被拒绝并留下审计。
- 批准 v1 后改为 v2，旧批准失效，必须 `/approve v2`。
- 5 个历史 Bug 或 1 个复杂 Issue 完成端到端修复。

## 6. 第 4 周：每日发版与通知

目标：候选 Issue 能通过 release 子 Agent 发布，失败可回滚。

任务：

- 06:00 由 Syntropy Automation 触发 release 任务。
- release 读取 `smartpipe:ready` 集合，生成 Release Note，执行完整测试和构建。
- 在本地/自托管环境构建制品，创建 GitHub Release 和 tag；需要签名时调用签名工具。
- 发布成功回写 `smartpipe:released` 并通知蓝信；失败保留制品、日志并回滚候选。
- 大版本保留人工发布确认和回滚开关。

验收：

- 连续 5 个工作日发版成功。
- 完成一次人为故障回滚演练。
- 发布通知包含 Issue 列表、版本号和升级提示。

## 8. 当前代码改造清单

- `backend/cmd/bot`：保留并增强入口能力。
- `backend/cmd/orchestrator`：改为任务网关/桥接，不再做完整状态机。
- `backend/cmd/issue-service`：退出主路径；持久化能力迁到桥接表/工具。
- `backend/cmd/runtime-manager`：新增运行时管理服务，包含 App Server 进程管理器、Go SDK 适配层（Master/Worker）和 HTTP adapter（`/api/agents`、`/api/agent-templates`）。
- `backend/internal/orchestrator`：删除规则分诊主路径，保留重复检测等工具函数。
- `backend/internal/mcp`：先实现一个 `smartpipe-mcp`。
- `configs/agents`：新增 `pipeline-lead`，保留 dev/test/release 作为按需模板；我们的服务不创建子 Agent。
- `deploy/docker-compose.yml`：保留 bot、桥接服务、smartpipe-mcp、数据库；不配置 GitHub Actions。
- `web/`：MVP 暂不投入。

## 10. Codex 模型配置（2026-11-06 完成）

模型配置在配置台「模型与推理」页完成，用户不再需要命令行参数。页面结构对齐
Syntropy 桌面端的模型配置：顶部默认模型，左侧供应商列表，右侧连接信息与模型目录。

数据与接口：

- `model_providers`：名称、Base URL、API 格式（`chat` / `responses`）、加密凭据 ID、启停、最近测试结果。
- `provider_models`：供应商下的模型目录；新目录项默认停用，手工添加可直接启用。
- `projects`：`codex_model_provider`、`codex_model`、`codex_reasoning_effort` 三个绑定字段。
- 默认模型：全局设置键 `codex_default_provider` / `codex_default_model` / `codex_default_effort`。
- 接口：`/admin/model-providers`（含 `/models` 目录、`/models/refresh`、`/test`、`/runtime`）、
  `/admin/model-default`。密钥只在服务端解密，管理接口只返回掩码。

生效链路：

1. 项目绑定了供应商与模型时，`codex-pipeline` 直接使用项目配置；未绑定则读全局默认模型。
2. 供应商的 Base URL 与 API Key 由 `/admin/model-providers/{id}/runtime` 下发，
   注入 `OPENAI_BASE_URL` / `OPENAI_API_KEY` 后再启动 Codex；同名环境变量以配置台为准。
3. 供应商停用、项目绑定的模型被删除时，新任务直接失败并给出明确错误。

验收：

- 页面可以新建供应商、保存连接、刷新模型目录、启停模型并测试真实请求。
- 项目选择供应商与模型后，流水线运行结果 JSON 的 `model` 为所选模型。
- 凭据只显示掩码；刷新与测试的错误信息会脱敏后返回界面。

## 11. 蓝信配置页（2026-11-06 完成）

配置台新增独立导航「蓝信配置」，页面包含四块：

- 应用连接：App ID、App Secret（密文、掩码）、API Base、测试连接；
- 群聊响应规则：仅响应 @机器人；
- 群到项目绑定：群 ID ↔ 项目，绑定时自动从其他项目移除同名群；
- 最近消息：蓝信入站消息与建单/派单状态。

生效链路：bot 启动时通过 `/internal/lanxin/config`（bot 内网令牌）读取配置，
运行期每 30 秒轮询一次，检测到 App ID / Secret / API Base 变化就重建 WebSocket 连接；
读取失败时回落到环境变量。配置台保存后无需重启服务。

静态预览：`docs/lanxin-config-demo.html`。

## 13. 配置台登录（2026-11-06）

- 用户名密码登录：`POST /admin/login`，成功后写 HttpOnly `smartpipe_session` Cookie。
- 会话：`GET /admin/session`、`POST /admin/logout`；会话过期或账号停用后自动失效。
- 账号来源：`SMARTPIPE_ADMIN_USER` / `SMARTPIPE_ADMIN_PASSWORD`；首次启动自动创建，
  密码变更需要 `SMARTPIPE_ADMIN_PASSWORD_RESET=true` 或直接改库。
- 兼容：流水线与脚本继续使用 `Authorization: Bearer $SMARTPIPE_ADMIN_TOKEN`。
- 页面：登录页按“左侧品牌说明 + 右侧登录表单”布局，登录后侧边栏显示当前账号和退出登录。
