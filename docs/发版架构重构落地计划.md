# 发版架构重构落地计划

> 版本：2026-11-15  
> 范围：SmartPipe 的 release v2 发版链路（SmartPipe 自己是工具，不发布自己）  
> 发布对象：Syntropy 等业务仓库
> 执行状态：P0–P4 完成并在真实 Syntropy 构建上实测；P5-1（plan/审批调用路径）与 P5-2（冒烟脚本三输入）已完成；P5-3 待真实升级服务 + 真实 GitHub 复核

## 1. 目标

一句话：**在控制台选「项目 + 升级服务器 + 构建机」，其余全部自动完成。**

- 输入只有三项，版本 / tag / commit / 说明 / 构建命令全部由项目配置和 GitHub 派生。
- 构建机只接收源码包，不再自己 `git clone`；一次产出全部制品和清单。
- Codex Agent 是这次发布的负责人：构建 → 制品 → 灌库 → 渠道推进 → GitHub 发布 → 失败诊断与修复。
- 全程无人工审批。
- 构建机环境问题也由 Agent 处理：它需要能探测、执行命令、看日志、读写文件。

### 当前流程（2026-11-15）

1. 控制台选择项目后调用 `GET /releases/v2/projects/{id}/release-preview`，从 `release_project_configs`、GitHub tag / commit / 说明和在线构建机中派生版本、平台、构建命令与可用执行器。
2. 点击「创建发布」调用 `POST /releases/v2/runs`，请求体只有 `project_id`、`executor_ids`、`update_server_ids` 和幂等键。
3. admin-api 创建 plan / run、绑定执行器、立即冻结源码包（GitHub tarball 优先，失败回落本地镜像 `git archive`），再启动 Codex Agent。
4. release-service 将 run 从 `queued` 推进到 `preparing`、`building`；release-executor 领取 target，下载冻结归档，解包后执行 build / verify，按规则发现制品、逐个上传并上报目标级清单，最后上报 `ready`。
5. 所有 target `ready` 后 run 进入 `verifying`。最后一个目标清单到达时 release-service 合并出 run 级清单；灌库、渠道和 GitHub 仍依赖 Agent 调 MCP。不可重试的 target 失败进入 `needs_attention`，等待 Agent 处理。
6. Agent 目前是一次性 Codex 会话，能通过 release-mcp 读运行、重试构建、灌库和发布，但不能远程探测/修复构建机环境，也不能在失败后被可靠地续会话唤醒。
7. 旧 plan / approval 的调用路径已删除：后端审批路由、MCP `release_approval_list`、前端审批 API/类型和存储实现均已移除；`release_v2_approvals` 表只保留历史数据兼容。

## 2. 边界

- SmartPipe 不发布自己；本文所有「发布」都指发布业务仓库（当前是 Syntropy）。
- 不保留人工审批：调用路径已删除；`release_v2_approvals` 表只做历史数据兼容。
- 构建机不直接访问源码仓库；源码只来自 admin-api 冻结的归档，保证可复现。
- Agent 只能通过 `release-mcp` 的受限工具做写操作，不直接连数据库。

```

                    │
                    ├── run + targets ──> release-service <── claim/heartbeat/complete ── release-executor
                    │                          │                                          │
                    │                          └──── artifacts + manifest ──> object store <┘
                    │
                    └── launch ──> Codex Agent ──release-mcp──> release-service / 升级服务 / GitHub
```

## 4. 状态机目标

```
queued → preparing → building → artifacts_ready → publishing → published
   │          │          │             │               │
   └──────────┴──────────┴─────────────┴───────────────┴──> needs_attention → recovering
                                                                   │                 │
                                                                   │                 └──> building / publishing
                                                                   └──> failed / blocked（终态）
```

规则：

- `failed` / `blocked` 是终态，只有 Agent 明确放弃或策略禁止时才进入。
- 单个 target 失败先重试；超过阈值进入 `needs_attention`，唤醒 Agent，不直接判死整次运行。
- `publishing` 阶段的每一步（灌库、渠道、GitHub）都必须可单步重试，且幂等。

约定：

- 展示版本 = `<version>.<提交日期 UTC>`，由 `build_version_template` 生成。
- 升级渠道的产品槽位只有 `desktop`，映射到完整安装器（`role=installer`）。Syntropy 客户端看到不带 `-thin` 的安装器文件名时只需要 `desktop` 这一格（`productSlotsForInstaller`），完整安装器本身已内含 mbot / nbot / node-repl / codex / node-runtime / app-server。若改成发布 thin 安装器，客户端会要求这 7 个槽位同时齐备，届时必须先把它们各自作为制品产出再映射。
- 制品 glob 必须只匹配安装包本体（`*.exe` / `*.dmg`）。同目录的 `checksums.sha256` 若被 glob 收进来，会和安装包争抢同一个槽位，`BuildUpgradeBundle` 会以「slot already provided」拒绝。
- 目标重试后，旧 attempt 的制品仍留在库里；`releasev2.CurrentAttemptArtifacts` 只保留每个 target 当前 attempt 的制品，避免旧安装包与新安装包争抢槽位。
- 清单由 `update-bundle.mjs` 生成，发布前必须通过 `verify-installers.mjs`。
- run 冻结的是 `v<version>` tag 指向的 commit，不是分支 HEAD；版本 tag 一旦发布就代表发版源码。
- `update-bundle.mjs` 的参数按源码版本自适应：`--installer-kind thin` 只在脚本支持时追加（`$(grep -q -- '--installer-kind' ... && printf ...)`），否则旧版本默认读 `dist/installers-thin`。同一个 profile 因此能同时发布 v0.5.17 与后续版本。
- 构建顺序必须是 **thin → full → update-bundle**：thin 构建会删除 `apps/desktop/resources/release-manifest.json`，full 构建最后重建它，`update-bundle.mjs` 依赖这份清单；反过来先 full 后 thin 会在清单缺失处失败（`ENOENT release-manifest.json`）。

### 本轮修复（2026-11-15 第五轮：P4/P5 全链路首次跑通）

run `rrun_2f57208fafc53523`（Syntropy 0.5.17，commit `f5d4af36`）从冻结源码到 `published` 全程无人工审批：
`artifact_verify` → `update_bundle_build` → `release_import`（cdn，`state=staged`）→
`github_release_sync`（draft → 2 个安装包 → 发布 → digest 回读）→ `update_channel_promote`（beta BOM）→ `release_publish`。

1. **槽位映射缺失导致 `bundle layout has no product slots`**：`update_service.productSlots` 必须显式配置。Syntropy 客户端看到不带 `-thin` 的完整安装器时只需要 `desktop` 一格，故映射 `{"desktop": {"artifactRole": "installer"}}`；thin 安装器则要求 mbot/nbot/node-repl/codex/node-runtime/app-server/desktop 七格齐备，当前不产出这七件独立制品，所以不发布 thin。
2. **制品 glob 过宽**：`dist/installers/<platform>/*` 把同目录的 `checksums.sha256` 也登记成 `installer`，与安装包争抢同一槽位。glob 收紧到 `*.exe` / `*.dmg`。
3. **重试后旧 attempt 制品混入发布**：新增 `releasev2.CurrentAttemptArtifacts`，只保留每个 target 当前 attempt 的制品，run 级制品（`target_id` 为空）不受影响。
4. **run 级制品被清单校验误判**：`upgrade_bundle` 是服务端生成的，不属于任何 target 清单；`manifestBlockers` 不再要求它出现在 run 清单里。
5. **bundle 重建摘要不稳定**：`BuildUpgradeBundle` 原先把 `now()` 写进 `metadata.createdAt`，同一 run 重建一次摘要就变，导致存储与登记不一致。改为锚定 `run.created_at`，并新增 `Store.ReplaceRunArtifact` 让 run 级制品可幂等覆盖。
6. **GitHub 资产上传把文件读成字符串**：`fake-github.mjs` 对整个 body 做 `Buffer.concat().toString()`，1 GB 安装包直接触发 V8 字符串上限；改为按块增量计算大小与摘要（真实 GitHub 无此问题，这是联调替身的缺陷）。

### 本轮落地（2026-11-16 第十八轮：attention 续跑复用同一个 Codex 线程）

1. **问题**：构建一次要 40–60 分钟，一轮 Agent 会话经常跑不完。以前的实现每轮都开新线程，Agent 会忘记「这台构建机缺什么、刚才修过什么」，续跑等于从零排查。
2. **实现**：
   - `codexrunner.Spec` 增加 `ResumeThreadID` / `PersistThread` / `OnThread`，`Result` 增加 `Resumed`。线程非 ephemeral 落盘，续不上时记日志并回退新线程，不让整轮直接失败。
   - `releaseagent` 由 `run.AgentThreadID` 决定续用；**线程一建立就通过 `OnThread` 落库**（`registerThread`），不再等本轮结束。
   - `store.SetReleaseV2RunAgentThreadID` 只更新 `agent_thread_id`，不碰 `updated_at`，避免破坏 attention 冷却窗口。
3. **实测发现并修复的真实缺陷**：第一版只在 `runner.Run` 返回后登记线程。演练里控制面重启把会话杀掉（`agent process lost`），线程 ID 根本没写进库，下一次只能开新线程——`rrun_73ba15aae6589d4d` 只有一条 `agent.thread{resumed:false}`。改成线程建立即落库后，同样的重启场景 `rrun_c7bdd34b0d351b6f` 的事件里第二轮 `resumed=true`，复用 `thread_id=01a1e10e-918a-72d2-b16f-3f40ecf851fa`。
4. **单测**：`TestThreadPersistedBeforeSessionEnds` 让假 runner 在 `OnThread` 之后阻塞，断言会话仍在运行时线程 ID 已落库；`TestLaunchResumesStoredThread` 覆盖续用路径。
5. **演练**：`release-v2-partial-resume-drill.sh` 增加线程复用断言与 `DRILL_MODEL_PROVIDER` / `DRILL_MODEL` 覆盖；实跑输出 `PARTIAL_RESUME_OK run=rrun_c7bdd34b0d351b6f`，并打印 `resumed 次数=1`。
6. **模型通道**：TeamoRouter（`mpr_e3601185`）余额不足（`insufficient_balance`），所有 Agent 会话秒失败；同环境 `qax`（`mpr_f886ecae`，`deepseek-v4-flash`）可用。演练用后者跑通，生产默认模型仍需充值或换供应商后再定。

### 12.2 关键实现顺序

1. **先定清单，再改上传。** 新增 `releasev2` 的清单 schema 和校验；executor 只在清单校验通过后上传，glob 仅作兼容兜底。run 级清单是后续灌库、GitHub 和审计的唯一事实来源。
2. **先有状态，再谈唤醒。** 在 `releasev2/types.go` 增加 `needs_attention` / `recovering`，runner 不再在 target 首次失败时直接 `fail`；超过重试阈值后只进入 `needs_attention` 并产生事件。

- 控制台入口只有项目、升级服务器、构建机；版本、tag、commit、说明、构建命令全部自动派生。
- 构建机从冻结归档构建，源码 sha256 可追溯；不存在构建时重新 clone。
- 每个平台产出可校验的制品清单，run 级清单能合并多平台并驱动灌库与 GitHub。
- 任一 target、环境、灌库或 GitHub 失败都能触发 Agent 诊断与修复；没有人工审批按钮或审批门禁。
- 最终状态只在 Agent 明确放弃或策略禁止时进入 `failed` / `blocked`；其余失败先进入 `needs_attention`。
- Syntropy v0.5.17 在测试环境完成一次无人值守全链路演练。

### 12.5 不可破坏的约束

- SmartPipe 不发布自己；所有发布对象都是业务仓库。
- 构建机不直接访问源码仓库，源码只来自 admin-api 冻结归档。
- Agent 的写操作只经过 release-mcp 和受审计的执行器命令，不直接连数据库。
- 迁移只追加，不复用 44–55；下一个可用编号是 56。
- **环境无关**：代码、Compose、镜像和脚本里不得写死任何 IP、主机名、账号或口令；示例一律用 `example.com` / `<placeholder>`，真实值只来自当前环境的配置。
- **无内置地址兜底**：任何对外地址只能来自「显式配置 → 当前请求上下文 → 服务注册记录」三级来源，不得用私有网段字面量当默认值。
- **可自动检查**：提交前执行 `scripts/check-hardcoded-endpoints.ps1`，发现私有网段 IP 字面量即失败。

### 12.6 环境地址与凭据从哪里来

| 配置项 | 来源 | 说明 |
| --- | --- | --- |
| 数据库地址 | `SMARTPIPE_DSN` | 部署机 `.env` 或安装参数 `--dsn`，不允许默认指向任何 IP |
| 构建机访问控制面的地址 | `SMARTPIPE_RELEASE_SERVICE_PUBLIC_URL` | 不填时按管理员请求的 `Host` / `X-Forwarded-Host` 与 `X-Forwarded-Proto` 推导 |
| 控制面对外端口 | `SMARTPIPE_RELEASE_SERVICE_PORT` | 默认 8099，仅是端口，不是地址 |
| 容器 DNS | `SMARTPIPE_DNS_PRIMARY` / `SMARTPIPE_DNS_SECONDARY` | 通用 Compose 不设默认值；需要固定解析时使用环境专属 `docker-compose.override.yml` |
| 需要固定解析的域名 | `deploy/docker-compose.override.yml` | 环境专属文件，不修改通用 compose |
| 升级服务器 | 控制台录入（URL + token） | 存数据库，按 run 选择，不进入代码 |
| 构建机 host / SSH | 控制台录入或 SSH 资源 | 只存在配置台，不进入代码 |
| 构建机执行器服务地址 | 接入命令中的 `SMARTPIPE_RELEASE_SERVICE_URL` | 由控制台按当前请求推导或 `PUBLIC_URL` 覆盖 |
| 控制台浏览器入口 | 部署环境的反向代理 / DNS | 前端只请求相对路径 `/admin`，不内置任何主机名 |
| 项目、构建机、升级服务器列表 | 数据库记录（控制台录入或执行器自注册） | 没有 seed 数据；全新安装时列表为空，地址全部来自当次录入 |
| 升级服务 / GitHub / S3 | `SMARTPIPE_RELEASE_UPDATE_URL`、渠道凭据、`SMARTPIPE_S3_*` | 全部按环境填写 |
| 测试与部署脚本 | `SMARTPIPE_TEST_DSN`、`SMARTPIPE_DEPLOY_HOST`、`SMARTPIPE_DEPLOY_USER`、`SMARTPIPE_SSH_PASSWORD` | 缺失时脚本直接报错，不使用内置默认值 |

地址解析顺序（所有组件一致）：

1. 显式配置：环境变量、安装参数或控制台录入；
2. 当前请求上下文：`Host`、`X-Forwarded-Host`、`X-Forwarded-Proto`；
3. 服务注册记录：容器服务名或数据库里的执行器 / 升级服务器记录。

三级都没有时直接报错并提示补充配置，绝不回落到代码里的私有地址。

- 不把版本、tag、commit 重新暴露成发布入口输入；它们只能来自项目配置和 GitHub 派生。
