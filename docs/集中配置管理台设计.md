# 集中配置管理台设计

日期：2026-11-05  
适用版本：主设计方案 v0.7.2

## 1. 目标

把所有项目、GitHub 地址、蓝信机器人配置、Syntropy 连接和凭据集中到一个管理界面中，避免：

- 每个服务各自读取环境变量或本地配置文件；
- 把 GitHub/蓝信 token 写进 Agent 提示词、任务消息或仓库；
- 新增项目时改代码、重启多个服务；
- 凭据散落导致无法轮换、审计和回收。

配置管理台是**管理员使用的基础设施界面**，不是管道监控看板。Agent 只能使用配置解析后的工具能力，不能读取凭据明文。

## 2. 角色与权限

MVP 阶段只设两类角色：

| 角色 | 权限 |
|---|---|
| 管理员 | 新增/编辑项目、配置凭据、测试连接、查看审计、轮换密钥 |
| 普通使用者 | 无管理台权限；通过蓝信或 GitHub 参与 Issue |

管理台必须登录后访问；首版可以使用 Syntropy 登录态或本地管理员账号，后续再接企业 SSO。凭据字段采用 write-only：保存后只显示掩码和最后 4 位，不能通过 API 读回明文。

## 3. 项目注册表

每个项目至少包含：

```text
project_id
name
description
github_provider          github | github_enterprise
github_repo_url
github_default_branch
github_issue_repo        owner/repo
github_labels_prefix     smartpipe
codeowners_required      true | false
approver_teams           维护者团队 / CODEOWNERS
verify_profile_path      smartpipe.yaml 或 Makefile
release_profile          版本规则、构建命令、制品目录
bluex_group_ids          绑定到该项目的蓝信群/会话
lead_agent_template      pipeline-lead 模板版本
mcp_tool_profile         lead / dev / test / release 的权限集
enabled                  true | false
```

项目解析规则：

- 蓝信入站消息先按 `group_id` / 私聊绑定找到 `project_id`；找不到时使用默认项目或提示管理员配置。
- GitHub Webhook 按 `installation_id + repo` 找到项目；找不到时拒绝处理并告警。
- 每个 Syntropy 任务都携带 `project_id`，lead 从配置服务读取项目策略，不把仓库地址硬编码在提示词里。
- 一个蓝信群可以绑定一个项目；一个项目可以绑定多个群或会话。

## 4. 凭据管理

### 4.1 支持的凭据类型

| 类型 | 用途 | 使用方 |
|---|---|---|
| GitHub App ID / private key / installation ID | 创建 Issue、评论、标签、分支、PR、Release | 桥接服务/工具层 |
| GitHub Webhook secret | 校验 GitHub 事件 | 桥接服务 |
| 蓝信 App ID / App Secret / API Base | 收消息、发消息、获取 WebSocket | bot 服务 |
| Syntropy Master URL / service token | 建任务、投消息、订阅事件 | 桥接服务 |
| Git SSH key（可选） | 拉取私有仓库 | 验证工作区 |
| 发布签名密钥（可选） | 制品签名 | 发版工具 |

Agent 永远不接收这些值。Agent 只看到工具名和 `project_id`；工具层在服务端解析项目并注入凭据。

### 4.2 存储与展示

- 数据库只存密文；使用 AES-GCM 或企业 KMS 加密，主密钥从部署环境注入，不存数据库。
- 日志、审计、错误响应、任务消息中禁止出现明文 token；统一脱敏。
- 管理台保存后只显示 `****last4`；更新时整段替换，不支持读回。
- 凭据支持启停、轮换和删除；轮换后立即失效旧值，并记录操作人。
- 每个凭据记录 `last_tested_at`、`last_test_result`，但测试结果不得包含 token。

### 4.3 连接测试

管理台提供“测试连接”：

- GitHub：用 App 安装身份读取目标仓库元数据，验证 Issue/PR/Contents 权限。
- 蓝信：获取 app token，验证 API 网关和机器人身份；不发送真实业务消息。
- Syntropy：读取 Master 健康状态或创建只读探测任务。
- Git：浅克隆目标分支，验证只读访问。
- 测试失败只显示错误码和可操作提示，不回显密钥。

## 5. Agent 模板与工具权限

管理台维护四类模板的版本和工具权限：

| 模板 | 外部通信 | 代码仓库 | 说明 |
|---|---|---|---|
| `pipeline-lead` | 蓝信、GitHub、Syntropy 管理/A2A | 可读，最终验证时可写 | 唯一对外通信接口；唯一创建子 Agent 的角色 |
| `dev-engineer` | 无 | 只读 | 不能被授予 GitHub/蓝信 token |
| `test-runner` | 无 | 只读 | 只回传测试报告 |
| `release-manager` | 无 | 只读/构建工作区 | 回传制品、Release Note 和发布结果给 lead |

`pipeline-lead` 是系统通信的唯一接口：

- 所有蓝信回复、GitHub 评论/标签/Issue 创建和发布通知都由 lead 发起。
- 子 Agent 只向 lead 回传结果，不直接给用户或 GitHub 发消息。
- 桥接服务只负责把入站事件路由给 lead，不代替 lead 创建子 Agent，也不直接对外发起业务沟通。
- 子 Agent 的 GitHub/蓝信工具权限默认为空；即使技术上可挂载，也不应在配置中授予。

## 6. 管理台页面

MVP 只需要以下页面：

1. **项目列表**：项目名、仓库、默认分支、蓝信绑定、启用状态、最近连接状态。
2. **项目详情**：GitHub 地址、Issue 仓库、验证契约路径、发版配置、审批人/CODEOWNERS、工具权限。
3. **凭据管理**：新增/轮换/停用 GitHub、蓝信、Syntropy、Git 凭据；显示掩码和最后测试结果。
4. **连接状态**：Webhook 最近事件、GitHub App 安装状态、蓝信 token 状态、Syntropy 可达性。
5. **Syntropy 运行时**：App Server、Master/Worker 节点、pipeline-lead 实例和生命周期操作；详细字段见 [Syntropy运行时管理设计.md](Syntropy运行时管理设计.md)。
6. **审计日志**：谁在什么时间修改了哪个项目/凭据/连接；不记录明文秘密。

运行时管理页面按源码核对后的三层能力边界设计（详见 [Syntropy运行时管理设计.md](Syntropy运行时管理设计.md)）：

- **App Server**：Runtime Manager 管理进程，负责启动、停止、重启、健康检查和日志；Go SDK 只是它的客户端。
- **Master / Worker**：通过 Go SDK 部署和检查（`Master.Deploy`、`Nodes.Deploy/Ensure/Progress/Ping/Delete`）。
- **pipeline-lead**：通过 App Server 的 `/api/agents` 部署，模板通过 `/api/agent-templates` 同步；当前 Go SDK 无这两个分组，由 Runtime Manager 的 HTTP adapter 承担。
- 页面不提供“创建子 Agent”入口；子 Agent 由 lead 自己派生。

暂不做：管道漏斗看板、Issue 列表复刻、自定义报表。这些先用 GitHub Issues/Projects 和日志。

## 7. 最小 API

```text
GET    /admin/projects
POST   /admin/projects
GET    /admin/projects/{id}
PATCH  /admin/projects/{id}
POST   /admin/projects/{id}/test-connections

GET    /admin/credentials
POST   /admin/credentials
PATCH  /admin/credentials/{id}
POST   /admin/credentials/{id}/rotate
POST   /admin/credentials/{id}/test

GET    /admin/audit
GET    /admin/health
```

所有管理接口要求管理员身份；写操作必须产生审计记录。凭据读取接口永不返回明文。

## 8. 与 Agent 的交互

- 创建任务时，桥接服务把 `project_id`、`issue_url`、`bluex_chat_id` 和工具白名单传给 lead。
- lead 调工具时只带 `project_id` 和业务参数；工具层自行解析凭据。
- 子 Agent 的任务消息只包含代码/测试所需信息，不包含 token。
- 如果项目被停用或凭据失效，工具返回明确错误；lead 通知管理员，不尝试用别的项目凭据。

## 9. 安全与审计

- 管理台和工具服务分离部署；管理台不直接持有 Agent 运行时令牌。
- 管理 API 做 CSRF、速率限制和会话过期控制。
- 凭据变更、项目绑定变更、工具权限变更全部审计。
- 数据库备份加密；备份中不出现明文秘密。
- 支持一键停用项目或吊销凭据，阻断后续任务。
- 管理员操作和 Agent 工具调用使用不同身份，日志可区分。

## 10. 验收

1. 管理员能在界面上新增项目，填写 GitHub 仓库地址、默认分支和蓝信群绑定。
2. 能配置 GitHub App、蓝信和 Syntropy 凭据，并执行连接测试；界面不回显明文。
3. 蓝信消息能按群绑定解析到项目；GitHub Webhook 能按仓库解析到项目。
4. lead 能用 `project_id` 调 GitHub/蓝信工具；子 Agent 的配置中没有外部通信工具。
5. 轮换 GitHub/蓝信凭据后，旧值立即失效，新任务使用新值。
6. 审计日志能看到配置变更，但看不到 token。
7. 停用项目后，新消息被拒绝或转入人工，不会继续创建任务。
