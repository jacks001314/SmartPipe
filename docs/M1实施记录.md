# M1 实施记录：蓝信 → GitHub Issue → pipeline-lead

更新时间：2026-11-05

## 1. 本轮交付的闭环

```
蓝信机器人消息
   │  POST /bridge/messages（X-Bridge-Token）
   ▼
桥接服务 bridge（:8090）
   ├─ 按 message_id 去重（bridge_links.source_message_id UNIQUE）
   ├─ 解析项目 → 仓库 + 标签（source:bluex / <labels_prefix>）
   ├─ 用凭据库创建 GitHub Issue
   ├─ 写映射（bridge_links）
   └─ 按 project_bindings 找到 lead → POST /api/agents/{id}/messages
                                          （App Server :8766）
GitHub Webhook → /webhooks/github
   ├─ HMAC-SHA256 验签（X-Hub-Signature-256）
   ├─ 按 X-GitHub-Delivery 去重（webhook_deliveries 主键）
   └─ 202 Accepted；重复投递返回 {"status":"duplicate"}
```

已实测：Issue 创建、重复消息只建一次单、Webhook 重复投递不重复处理、派单成功写入 `dispatch_status=sent`。
管理台新增「桥接与派单」页：项目绑定、消息映射、派单记录、Webhook 投递四块视图。

## 2. 数据表

迁移见 `backend/internal/store/migrate.go`（v2、v3、v4）。

| 表 | 用途 | 关键约束 |
|---|---|---|
| `bridge_links` | 一条来源消息 ↔ 一个 Issue | `source_message_id UNIQUE`；`dispatch_status` 取 pending/skipped/unbound/sent/failed |
| `webhook_deliveries` | GitHub Webhook 投递去重 | `delivery_id PRIMARY KEY` |
| `project_bindings` | 项目 → App Server → lead | `project_id PRIMARY KEY`，一项目一 lead |
| `bridge_dispatches` | 每次派单尝试 | 关联 `bridge_links.id`，失败保留原因 |

`project_bindings.agent_project_id` 记录 lead 在 Syntropy 里的项目归属。投递消息的 `projectId` 必须用它：
App Server 会校验 Agent 归属，跨项目投递返回 **HTTP 412**
（`agent "xxx" belongs to project "prj_sandbox", not "prj_xxx"`）。这一条来自真实运行验证，不是推测。

## 4. 接口

桥接服务（:8090，`X-Bridge-Token`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/bridge/messages` | 入站消息；新建返回 201，重复返回 200 且 `created=false` |
| GET | `/bridge/links` | 最近映射（调试用） |
| POST | `/webhooks/github` | 验签 + 去重，返回 202 |

管理台（:8092，Bearer）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/bridge/links` | 映射列表 |
| GET | `/admin/bridge/dispatches` | 派单记录 |
| GET | `/admin/bridge/deliveries` | Webhook 投递 |
| GET | `/admin/bridge/bindings` | 项目绑定 |
| PUT | `/admin/bridge/bindings/{projectId}` | 绑定 lead；未给 `agent_project_id` 时向 App Server 查询 Agent 归属 |
| DELETE | `/admin/bridge/bindings/{projectId}` | 解绑 |
| POST | `/admin/bridge/links/{id}/redispatch` | 重试派单（不会重复建 Issue） |
| POST | `/admin/runtime/app-servers/{id}/agents` | 部署 lead，`bind_lead=true` 时自动绑定 |

## 8. 复杂 Issue 审批门禁（已实现并通过端到端验证）

用户要求：复杂 Issue 必须先讨论，维护者确认后才能开工。实现方式是在 GitHub 评论里使用两条命令，
服务端做权限、版本与内容指纹校验，批准后自动通知 lead。

```
lead:      /plan <方案正文>       → issue_plans 新增 vN，回评“指纹 + /approve vN”
maintainer:/approve vN            → 校验 author_association ∈ {OWNER, MEMBER, COLLABORATOR}
                                   → 校验 vN 存在且内容哈希未变
                                   → 写 issue_approvals，打 approved 标签
                                   → 通知绑定的 pipeline-lead 开工
```

| 表 | 用途 |
|---|---|
| `issue_plans` | 每个 Issue 的方案版本；`UNIQUE (repo, issue_number, version)` |
| `issue_approvals` | 批准记录；同版本重复批准返回 duplicate，不会重复通知 lead |

校验规则：

1. 非维护者执行 `/approve` 直接拒绝，并在评论里说明需要的权限。
2. 方案不存在、版本不存在都会拒绝并回评。
3. 批准时重新计算 `sha256(归一化方案正文)`，与登记值不一致即拒绝（防止批准后被改写）。
4. 重复投递由 `webhook_deliveries` 主键拦住；重复批准由唯一约束拦住。
5. 方案正文统一 `\r\n` → `\n`、去首尾空白后再哈希，跨平台稳定。

2026-11-05 实测（本地假 GitHub + 真实 bridge 进程）：

```
[issue_comment] http=202 {"approval":{"action":"plan_created","version":1,"hash":"sha256:5874b477..."}}
[issue_comment] http=202 {"approval":{"action":"approved","version":1,"hash":"sha256:5874b477..."}}
```

假 GitHub 收到两条评论：

1. `方案 v1 已登记，内容指纹 \`5874b477d46a\`。请维护者审阅后评论 \`/approve v1\`…`
2. `✅ 方案 v1 已批准（审批人 @maintainer，指纹 \`5874b477d46a\`）…`

`GET /admin/bridge/plans` 返回 `approved=true, approver=maintainer`；批准后 lead 收到开工消息。

脚本：`scripts/approval-smoke.ps1 -Issue <编号> -Repo owner/repo`（需要 bridge 已配置 webhook secret）。

## 9. 蓝信回执

建单成功后，bridge 调 bot 的内网接口把 `issue_url` 回给来源会话：

```
POST @bot /internal/reply   X-Internal-Token: <SMARTPIPE_BOT_INTERNAL_TOKEN>
{"chatType":"group","targetId":"<chat_id>","refMsgId":"<message_id>","text":"已收到反馈，已创建 GitHub Issue #N：<url>…"}
```

* 群消息回 `chat_id`，私聊回 `user_id`；`refMsgId` 让蓝信引用原消息。
* `bridge_links.receipt_status` 记录 `sent / failed / skipped`，失败原因写 `receipt_error`，不影响建单与派单。
* 配置：`SMARTPIPE_BOT_ADDR`（如 `http://127.0.0.1:8091`）与 `SMARTPIPE_BOT_INTERNAL_TOKEN`；不配置时状态为 skipped。
