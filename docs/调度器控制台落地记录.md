# 调度器控制台

日期：2026-11-09　范围：单 worker 暂停/恢复/重试/停止、状态观察、Codex 实时输出

## 1. 本次落地

控制台新增“运行中心 / 调度器”页面，可查看 worker 状态、当前动作、运行时长、心跳和事件时间线，并对单个 worker 执行暂停、恢复、重试、停止。页面下方同时展示最近蓝信消息流水，能看到消息是已回答、已建单、待补充、未绑定还是失败。

worker 详情默认进入“实时输出”，把 Codex app-server 的流式通知投影成可读卡片：

- Agent 消息和计划用 Markdown 渲染。
- 命令显示命令、工作目录、退出码和耗时，长输出放在可滚动终端区域。
- 文件变更显示文件名和增删行，差异按文件折叠。
- 推理只展示 summary，不展示原始思维链。
- 引擎错误、告警和模型切换单独提示。
- 命令失败时自动展开；用户向上翻后不会被新输出强制拉回底部，并显示“有 N 条新输出”。

暂停语义：只暂停指定 worker。暂停会取消这一轮 Codex 执行，保留分支与工作区；恢复后重新排队。全局新任务领取、其他 worker 不受影响。

## 2. 调度器状态与执行

- 新增 `paused` 状态，`ActiveStates()` 仍只包含 `preparing/coding/verifying/pushing`，暂停不占并发名额。
- 每个执行中的 worker 注册可取消的 `context.CancelFunc`，暂停和停止会取消当前 turn；同一 worker 最多只有一个执行 goroutine。
- 执行失败、暂停、停止和 Issue 关闭都会检查最新数据库状态，避免被取消的旧 goroutine 覆盖新状态或继续推送 PR。
- 执行期每 20 秒更新 `heartbeat_at`。超过 2 分钟没有心跳且没有本地执行 goroutine 的活跃 worker，会被标记为 `blocked`。
- 调度器启动时检查遗留的活跃 worker，只有心跳已过期的记录会转为 `blocked`，避免进程重启后永久占用并发名额。
- Reconcile 现在也检查活跃状态；Issue 关闭时取消执行并收尾。

## 3. Codex 实时输出

`codexrunner.Spec` 新增 `OnEvent` 回调和原始通知结构。调度器在 `RunStreamed` 的消费循环里拿到每条通知后立刻投影，因此不会再出现“只有最终结果，没有过程”的情况。

投影规则与 Syntropy 桌面端保持一致：

- `item/agentMessage/delta` → Agent 消息正文。
- `item/plan/delta`、`turn/plan/updated` → 计划。
- `item/reasoning/summaryTextDelta`、`summaryPartAdded` → 推理摘要。
- `item/reasoning/textDelta` 有意丢弃，不把原始思维链写入数据库。
- `item/commandExecution/outputDelta`、`item/fileChange/outputDelta` → 命令或文件输出。
- `item/fileChange/patchUpdated` → 同一文件变更 item 的实时增删行。
- `turn/diff/updated` → 本轮完整变更。
- `thread/tokenUsage/updated` → token 用量。
- `error / configWarning / guardianWarning / deprecationNotice / model/rerouted` → 系统提示。

同一条 item 的增量在内存中合并，约每 350 ms 刷新一次数据库，前端按 `item_id` 原位替换。终态、暂停和停止会强制 flush；暂停或取消时，仍在运行的 item 标记为 `cancelled`。

输出清理包括 ANSI 控制序列、常见 token/API key/password 形态的脱敏，以及单 item 4 MiB 硬上限。超过 64 KiB 的正文写入 `SCHEDULER_OUTPUT_DIR`，数据库只保留首尾各 4 KiB 摘要；完整正文通过分页接口读取。外置写入先写临时文件再 rename，避免读到半截日志。

## 4. 数据

迁移 30 `scheduler_observability`：

- `scheduler_workers` 增加 `issue_title`、`priority`、`queued_at`、`started_at`、`state_changed_at`、`heartbeat_at`、`finished_at`、`round`、`model`、`provider_id`、`pr_url`、`blocked_reason`。
- 新增 `scheduler_worker_events`，记录状态迁移、领取、轮次、验证和人工操作。

迁移 31 `scheduler_worker_outputs`：

- 每个 `(worker_id, item_id)` 一行，保存类型、状态、标题、摘要正文、元数据、外置引用和 revision。
- 更新旧 item 时分配新的全局 revision；SSE 和分页接口用 revision 做游标，不依赖时间戳。
- 大日志落在 `SCHEDULER_OUTPUT_DIR/<worker>/<item>.log`。

## 5. 接口

消息流水直接复用 `lanxin_messages`：调度器在收到消息时写入 `processing`，处理结束后更新为 `answered / need_info / issue_created / issue_updated / unbound / failed`，失败原因保留在 `reason`。

调度器内网：

```text
GET  /internal/scheduler/overview
GET  /internal/scheduler/workers
GET  /internal/scheduler/workers/{id}
GET  /internal/scheduler/workers/{id}/output?after=<revision>&limit=500
GET  /internal/scheduler/workers/{id}/output/{item}/raw?offset=<byte>&limit=<byte>
GET  /internal/scheduler/workers/{id}/stream?after=<revision>
POST /internal/scheduler/workers/{id}/action   {"action":"pause|resume|retry|stop"}
```

管理台：

```text
GET  /admin/scheduler/overview
GET  /admin/scheduler/messages
GET  /admin/scheduler/workers/{id}
GET  /admin/scheduler/workers/{id}/output
GET  /admin/scheduler/workers/{id}/output/{item}/raw
GET  /admin/scheduler/workers/{id}/stream
POST /admin/scheduler/workers/{id}/action
```

SSE 使用标准 `id:` / `event: outputs` 帧；客户端断线后带最后 revision 重连即可补齐。空闲连接每 15 秒发送 keep-alive 注释帧；连续失败后前端退回 2 秒轮询。

管理台通过 `SMARTPIPE_SCHEDULER_URL` / `SMARTPIPE_SCHEDULER_TOKEN` 代理调度器内网接口；所有控制动作写入审计日志。

## 6. 配置

`admin-api` 新增：

```text
SMARTPIPE_SCHEDULER_URL=http://127.0.0.1:8098
SMARTPIPE_SCHEDULER_TOKEN=<SCHEDULER_TOKEN>
```

调度器新增：

```text
SCHEDULER_OUTPUT_DIR=/data/scheduler-outputs
```

docker-compose 的 admin-api 使用 `http://scheduler:8098`，token 复用 `SCHEDULER_TOKEN`；调度器卷增加 `./data/scheduler-outputs:/data/scheduler-outputs`。systemd 部署默认使用 `@STATE_DIR@/scheduler-outputs`。

## 8. 已知边界

- 消息流水展示最终判定与原因，暂未展示 chat worker 的逐轮过程或 token 成本。
- 原始思维链按产品约束不落库；只保留 Codex 自己生成的 reasoning summary。
- 全局暂停领取、队列拖拽排序、成本预算尚未实现。
- 本机没有运行中的 Postgres，迁移 31 通过编译与迁移顺序测试验证，尚未在真实数据库执行。
