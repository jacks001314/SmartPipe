# 发版 v2 运维手册

SmartPipe 是发版工具，本身不发版；发布对象是被配置的项目（当前为 Syntropy）。本手册只描述发版 v2（`/admin/releases/v2/*`）的日常运维。

## 1. 入口只有三个输入

| 输入 | 来源 | 说明 |
| --- | --- | --- |
| 项目 | `projects` 表（GitHub 仓库、默认分支） | 版本、tag、commit、构建命令、制品规则都从项目配置派生 |
| 升级服务器列表 | 发版设置里的 `update_services`（url + 凭据名） | 可多选，并行导入，单台失败只重试该台 |
| 构建机 | `release_v2_executors`（在线状态） | 构建机只拉冻结源码包，不 clone 仓库 |

提交 `POST /admin/releases/v2/runs`，body 只需 `project_id` / `update_server_ids` / `executor_ids`（演练可加 `mode=build_only`）。没有 plan、没有审批步骤。

选中项目后，预览（`GET /admin/releases/v2/projects/{id}/release-preview`）会并行查一遍启用的升级服务：如果派生出的版本已经存在，返回 `warnings[code=version_already_published]`，界面上直接标黄。它不阻止创建，但值得在按下按钮前处理——同版本只有在制品字节完全一致时才安全，而构建不可复现，`release_import` 大概率会把它拦下来。预检结果缓存 60 秒。

## 2. 一次发布的正常路径

1. `queued → preparing`：核对目标构建机在线。
2. `building`：控制面冻结源码包，执行器领取目标，按项目配置的 build / sign / verify 命令执行，产出制品清单并上传。
3. `artifacts_ready`：Agent 核对制品（`artifact_list` / `artifact_verify`）。发布说明优先用仓库里的 `notes_path`；文件不存在时，服务端按上一版 tag 到本次提交的改动自动生成「## 更新日志」，Agent 不得覆盖已有更新日志。
4. `release_import`：生成升级包并并行上传到全部选中的升级服务（不移动渠道指针）。
5. `github_release_sync`：草稿 → 上传全部资产 → 发布 → 回读 digest。
6. `release_publish`：推进渠道指针（CAS + 回读），失败自动回滚。
7. `published`（或 build_only 的 `built`）。

全程无人工审批。Agent 会话中途结束不影响状态机：目标还在构建时 run 保持 `building`，目标齐备后自动继续。

## 3. 出问题时先看什么

```bash
# run 状态、目标、制品
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8092/admin/releases/v2/runs/<run_id>"

# 事件（含 Agent 工具调用与构建日志分片）
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8092/admin/releases/v2/runs/<run_id>/events?limit=500&after=<last_id>"
```

事件里按顺序找这几类，就知道卡在哪一步：

- `run.needs_attention`：有失败目标，`error_code` / `error_message` 指向具体原因。
- `agent.attention_resume`：Agent 已自动接管（正常应在失败后数秒内出现）。
- `mcp.tool` + `executor_probe` / `executor_exec`：Agent 在构建机上做的诊断与修复，命令与结果都进 `release_executor_commands` 审计表。
- `build_retry` / `target.retry_requested`：修复后重新排队。
- `release.import.partial`：部分升级服务失败，`retry_services` 列出只该重试的服务。

## 4. 构建机环境问题

Agent 会自己处理，不需要人工登录。典型链路（2026-11-16 实跑）：

1. 目标失败 → `needs_attention` → 2 秒内 Agent 接管。
2. `executor_probe` 看 PATH、工具位置、磁盘、Xcode/Node/pnpm 版本。
3. `executor_logs` / `executor_files` / `build_logs` 定位坏掉的文件。
4. `executor_exec` 执行白名单内的修复命令（`ln -sfn`、`rm`、`mkdir`、`brew`、`launchctl` 等），每条都带 actor / run_id / 退出码。
5. `build_retry` 重新构建并继续上传。

执行器白名单命令目前覆盖：构建工具（node/npm/pnpm/yarn/go/git/xcodebuild/xcrun/codesign/hdiutil/security/brew）、文件与管道（ls/du/df/mkdir/cp/mv/rm/chmod/ln/cat/tail/grep/sed/awk/find/tar/zip/curl/stat 等）、macOS 诊断（file/otool/lipo/plutil/pkgutil/spctl/xattr/ditto/install_name_tool/launchctl）。`sudo` 永远拒绝；不在白名单的命令返回 126 并记录原因（遇到时考虑是否应加入白名单，而不是改用别的命令绕过）。

## 5. 构建机执行器重装 / 升级

控制台「构建机」页或直接调接口：

```bash
POST /admin/releases/v2/executors/deploy
{"id":"mac-01","os":"darwin","arch":"amd64","host":"<ip>","port":22,
 "username":"<user>","auth_type":"password","secret":"<password>"}
```

服务端从镜像里的 `/app/bin/executors/<os>-<arch>/release-executor` 取二进制，上传、写 `executor.env`、重启 launchd 服务并等注册上线。构建机上的 `bin/` 目录（Agent 安装的 node/go 等软链）不会被清掉。

**改过 executor 代码后一定要重装构建机执行器**，否则控制面在跑新逻辑、构建机还在跑旧二进制。典型症状：交叉平台的制品被登记成构建机自己的平台（例如全部是 `darwin/arm64`），拼 bundle 时报 `slot ... already provided`。

## 6. 升级服务与 GitHub

- 升级服务凭据在「发版设置」里登记名字（如 `cdn_token` / `app_token`），项目配置里引用名字，不写地址和口令。
- `release_import` 的 `partial` 是预期行为：只对 `retry_services` 再次调用并传 `services=[...]`。
- `release_import` 以「槽位 + 平台 + 架构」为键，摘要一致就跳过；工具调用超时/中断后用同样参数再调一次即可续传，不会重传已完成的制品（全量约 2.4 GB，慢链路会走到这一步）。
- 单次 MCP 工具调用上限由 `SMARTPIPE_RELEASE_AGENT_TOOL_TIMEOUT_SEC` 控制（默认 1200 秒）。
- GitHub 凭据按仓库逐个校验可读性后自动挑选；`github_release_get {"tag":"v0.5.17"}` 可在发布前读远端现状。
- 同版本重发：复用已有 Release，删除「名字含本次版本号但不在本次清单」的旧资产，记录 `github.asset_removed`。

## 7. 已知限制

- 制品成功但 GitHub 无 Release 时，`release_publish` 会落到 `partially_published`：先跑 `github_release_sync` 再 `release_publish`。
- 构建机磁盘需预留约 16 GB；Electron 全量构建会吃掉数 GB，必要时清 `~/Library/Caches/go-build`。
- 构建机没有 sudo 权限，需要特权的修复目前只能人工介入（`executor_probe` 会报 `sudo=requires-password`）。
- 控制面重启会杀掉进程内的 Agent 会话；还在构建的目标不受影响，run 不会被打回 `needs_attention`，构建完成后自动继续。

## 8. 环境地址从哪来

产品代码、部署模板、脚本里不写任何 IP / 地址 / 口令；地址来自部署时的 `deploy/.env` 与「发版设置」，可用 `scripts/check-hardcoded-endpoints.ps1` 校验。

## 9. 项目发版配置（profile 文件）

仓库里的 `deploy/profiles/syntropy-release-config.json` 是 Syntropy 的完整发版配置：两个构建目标、36 条制品规则、升级服务的 9 个产品槽位 + `templates` / `skills` 两个内容组件。文件不含项目 ID、升级服务地址或凭据，换环境时只需按环境补这三样。

```bash
# 取当前配置并备份
GET  /admin/releases/v2/projects/<project_id>/release-config

# 应用 profile（先补 project_id / update_server_ids）
PUT  /admin/releases/v2/projects/<project_id>/release-config
```

要点：

- 产品槽位一个都不能少。Syntropy 客户端按 9 个槽位判断「这一版能不能装」；只发 `desktop` 会把渠道指针里的其它成员一起抹掉，Windows 也会缺 `computer-use` / `computer-use-notices`。
- 交叉产出靠制品规则上的 `os` / `arch`：一台 mac 构建机同时产出 windows / linux 组件，槽位平台取制品自身平台，不取构建机平台。
- 内容组件版本不用写：bundle 会从 `<component>-<x.y.z>.tar.gz` 文件名读版本，与仓库里的 `tools/content-release.json` 对齐。
- `desktop` 槽位放完整安装器；`*-thin` 只用于增量更新，不进产品槽位。
- 新增/修改 profile 后跑 `go test ./internal/releasev2 -run TestBundledProjectProfiles`，它会检查配置能解析、且规则能拼出完整 bundle。

## 10. 真实制品全链路演练

`scripts/release-v2-chain-drill.sh` 用目标项目现成的发版配置和构建机，在替身升级服务 / 替身 GitHub 上跑一次「项目 + 升级服务器 + 构建机 → published」，**不碰线上渠道**：

```bash
sudo CHAIN_PROJECT_ID=<project_id> CHAIN_EXECUTOR=<executor_id> \
  bash scripts/release-v2-chain-drill.sh
```

- 脚本会备份并临时改写发布设置，退出（含失败）时自动恢复，同时停掉替身。
- 全程由 Agent 自己调 `release_import` → `github_release_sync` → `release_publish`，没有人工步骤。
- 收口断言：两台替身的产品发布槽位单元数量、内容组件版本、渠道 BOM 一致，替身 GitHub 的 Release 已发布且有附件。
- 演练会真跑一次完整构建（Syntropy 约 40–60 分钟）；构建机磁盘至少留 10 GB，NSIS 打包阶段会吃掉数 GB。

## 11. 半发布（partially_published）自动接管演练

`scripts/release-v2-partial-resume-drill.sh` 验证「渠道已推进、GitHub 没收口」这条路径能被自动接管，不需要任何人工点击。用合成项目 + 秒级假构建，全程约 3 分钟：

```bash
sudo bash scripts/release-v2-partial-resume-drill.sh
```

- 替身 GitHub 从开始就返回 503 给「公开草稿」PATCH。`github_release_sync` 是直接建出已发布 Release（不发 PATCH），所以唯一被拒绝的是 `release_publish` 收口那次调用——`partially_published` 因此是确定性结果，不依赖抢时间窗口。
- 脚本随后重启 `smartpipe-app-1` 杀掉仍在重试的 Agent 会话，断言运行**仍然**停在 `partially_published`（证明旧实现会在这里永久卡住），再放开 GitHub 并等待 `attention_resume` 自动续跑到 `published`。
- 收口断言：事件链里有 `agent.attention_resume`（`from=partially_published`）、至少一条 `resumed=true` 的 `agent.thread`（证明续跑复用同一个 Codex 线程而不是重开）、渠道 BOM 已落库、GitHub Release 已发布且有附件。
- 默认供应商余额不足时，用 `DRILL_MODEL_PROVIDER` / `DRILL_MODEL` 给演练项目单独指定可用模型，不影响全局默认：

  ```bash
  sudo env DRILL_MODEL_PROVIDER=mpr_f886ecae DRILL_MODEL=deepseek-v4-flash \
    bash scripts/release-v2-partial-resume-drill.sh
  ```
- 成功输出 `PARTIAL_RESUME_OK`；退出（含失败）时恢复发布设置、停掉替身。若脚本被 `SIGKILL` 打断，用 `deploy/data/drill/partial-<stamp>/settings.backup.json` 手动恢复。
- 替身 GitHub 的故障注入：`POST /__hold {"on":true}` 拒绝所有发布 PATCH；`POST /__hold {"after":N}` 放行前 N 次、之后 503（`N=0` 时回到 `on` 语义）。

## 12. 同版本换字节拦截演练

`scripts/release-v2-version-gate-drill.sh` 验证「版本号没变但制品字节变了」不会静默改写线上同版本槽位，全程约 2 分钟：

```bash
sudo bash scripts/release-v2-version-gate-drill.sh
```

- 第一次：合成项目 `0.9.80001` 正常发到 `published`，记录替身上 `app` 槽位的摘要。
- 第二次：同版本、新运行；构建脚本写入纳秒时间戳，字节必然不同。Agent 调 `release_import` 会拿到 `version_already_published`，事件里出现 `version_conflicts`，运行停在 `artifacts_ready`。
- 收口断言：第二次运行没有 `published`、替身同版本槽位摘要与第一次完全一致。成功输出 `VERSION_GATE_OK`。
- 真实发版遇到这个拦截时的正确动作是**提升版本号**，不要在 `release_import` 上带 `replace_existing`；同版本换字节已装客户端不会升级。

## 13. 发一个真实版本（生产）

版本号提升在源码仓里做，一次提交一个 tag；之后三输入就够，不需要再碰构建机和升级服务。

```bash
# 1. 在业务仓（例如 Syntropy）里升版本并打 tag，必须推到远端：
cd /path/to/Syntropy
git checkout main && git pull --ff-only
node -e 'const fs=require("fs");for(const f of ["desktop_app/package.json","desktop_app/apps/desktop/package.json"]){const p=JSON.parse(fs.readFileSync(f));p.version=process.argv[1];fs.writeFileSync(f,JSON.stringify(p,null,2)+"\n")}' 0.5.18
git commit -am "release: v0.5.18" && git tag v0.5.18 && git push origin main v0.5.18

# 2. 控制台「新建发版」只填三项：项目、升级服务器（app/cdn）、构建机（mac-01）。
#    预览里 warnings 为空即表示这个版本还没发过；有 version_already_published
#    说明版本号没升，回去补第 1 步。
```

- 发版运行会先冻结源码包（按 tag 解析 commit），构建机只收这个包，不再 clone。
- 全流程由 Agent 驱动；构建机环境问题（执行器损坏、磁盘/Cache 不足、缺工具链）由 Agent 自己取证并修复后重试。
- 收口只看三处：运行到 `published`、升级服务上该版本 BOM 与服务端回读一致、GitHub Release 已发布且有全部附件。
- 失败停在 `needs_attention` / `partially_published` 时不用人工点：attention worker 会接管（事件 `agent.attention_resume`），续跑复用同一个 Codex 线程（`agent.thread{resumed:true}`）。
