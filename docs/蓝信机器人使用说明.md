# 蓝信机器人使用说明

适用对象：SmartPipe 项目群的成员
机器人名称：以群内实际显示为准（例如 @stropy）

## 这个机器人能做什么

它把蓝信群里的提问和问题反馈接到项目仓库：

- 回答产品使用、代码实现和排障类问题，必要时会读取项目代码核对；
- 判断一条消息是否描述了真实缺陷或明确需求；
- 先生成待确认的 Issue 草稿并发回群里；群成员明确确认后才创建 GitHub Issue，交给 Codex 修复、验证并提交 PR；
- 把建单、进展和结果同步回群里。
- 查看 Issue 的 worker 状态，并在群里暂停、恢复、重试、停止或重新排队。

群消息是入口，GitHub Issue 是完整过程，PR 是代码结果。机器人不是即时客服，也不会在聊天中直接改代码或合并 PR。

## 开始使用前

群聊默认必须 **@机器人**，没有 @ 的消息不会被处理。第一次使用前，请联系管理员确认：

1. 这个群已经在 SmartPipe 配置台绑定了项目；
2. 项目已经配置可用的 GitHub 凭据；
3. 机器人在线。

如果群没有绑定，机器人会回复“这个群还没有绑定项目”；如果项目没有 GitHub 凭据，会提示先由管理员配置。遇到这两种情况，把提示截图发给管理员即可。

## 三种最常用的用法

### 1. 提问：先问清楚，再决定要不要建单

适合产品怎么用、某个报错怎么处理、代码为什么这样实现这类问题。

写法：

```text
@机器人 导出报表时一直提示“任务排队中”，v2.3.1，Windows 11，今天 10 点后开始出现。昨天同一账号还正常，可能和哪块有关？
```

尽量带上：使用的版本、操作系统或浏览器、账号角色、报错原文、出现时间、已经尝试过什么。问题复杂时附一张截图或一段脱敏日志。

如果你只是想讨论方案，不想马上建单，可以在开头写明：

```text
@机器人 先讨论方案，不要建单：...
```

机器人会给出判断，但不会直接建单；真正创建前仍会发草稿到群里等待确认。

### 2. 报缺陷或提需求：按模板写，机器人才能一次处理对

第一行写一句能当 Issue 标题的话，后面按“环境、复现、实际、期望、影响、频率”补充。示例：

```text
@机器人 【缺陷】批量导入后列表偶尔少 3 条数据

环境：SmartPipe v0.3.2，Windows 11，Chrome 131，管理员账号
复现：
1. 打开“数据导入”，选择包含 100 行的 CSV
2. 点击导入并等待完成
3. 刷新列表，只显示 97 行
实际：提示导入成功，但列表少 3 条
期望：100 条全部导入，并给出失败行明细
频率：5 次里出现 2 次
影响：财务对账需要人工补数据
附件：导入文件（已脱敏）、页面截图、request id
```

机器人会先查找同一项目内标题相同且未关闭的 Issue：命中就追加到已有 Issue；没有找到时，只生成待确认草稿。草稿会列出标题、级别和摘要，并给出草稿编号。群成员回复“@机器人 确认建单 DRAFT-xxxx”后才会创建 Issue 并进入修复队列；回复“@机器人 取消建单 DRAFT-xxxx”则只取消草稿。草稿 30 分钟内有效，确认前不会建单，也不会派 worker。

### 3. 补充已有 Issue：带上编号

需要补充复现信息、日志、环境或新现象时，在消息里带上 Issue 编号：

```text
@机器人 补充 #123：这个问题在 Windows 10 也能复现，日志如下...
```

也可以直接贴 Issue 链接。机器人会把内容追加到该 Issue，并唤醒对应的修复任务。只引用旧消息、不写编号时，机器人可能无法判断你要补充哪个 Issue；如果它回复“没能确定要更新哪个 Issue”，补上 `#编号` 再发一次即可。

## 怎样描述，机器人才能处理对

| 建议写清楚 | 原因 |
|---|---|
| 版本、系统、浏览器、账号角色 | 很多问题只在特定环境出现 |
| 从哪一步开始、点击了什么、看到什么 | 便于复现和定位 |
| 实际结果与期望结果 | 区分缺陷和需求 |
| 完整报错文字、request id、trace id | 截图里的报错无法搜索，文字更容易定位 |
| 影响范围和紧急程度 | 决定优先级 |
| 出现频率 | 偶现和必现的排查方式不同 |
| 已经尝试过的办法 | 避免重复建议 |

避免这样发：

```text
@机器人 导出有问题，帮看下
```

这条消息缺少环境、复现步骤和报错信息，机器人通常只能追问，无法生成可确认的建单草稿。

一次只发一个主题。多个互不相关的问题混在一条消息里，机器人很难拆成准确的 Issue；拆开发送，并分别说明影响。

## 图片、文件和日志

- 可以随消息发送截图、PDF、文本、日志、JSON、配置文件等附件；
- 一条消息最多处理 4 个附件，单个文件不要超过 8 MB；
- 崩溃上报的 `crash_bundle.json` 上限为 256 KB，且需要管理员开启该能力；
- 截图请圈出关键位置，同时把关键报错复制成文字；
- 语音和视频不适合作为唯一信息，请补一段文字说明。

发送日志前先脱敏：删除账号密码、访问令牌、身份证号、手机号、客户姓名、内部地址等敏感信息。

崩溃附件解析成功后，机器人会在群里发送 `【待确认建单】DRAFT-xxxx`，列出崩溃标题和摘要。确认前只保存草稿与崩溃记录，不创建 Issue、不派 worker；回复确认命令后才建单并进入修复队列。

## 群内可用的命令

| 写法 | 作用 |
|---|---|
| `@机器人 你的问题` | 提问、报缺陷、提需求 |
| `@机器人 补充 #123：...` | 把内容追加到 Issue #123 |
| `@机器人 确认建单 DRAFT-xxxx` | 确认当前待确认草稿并创建 Issue |
| `@机器人 取消建单 DRAFT-xxxx` | 取消当前待确认草稿，不创建 Issue |
| `/status #123` 或 `有派发worker吗` | 查看 Issue 的 worker 状态、分支和 PR |
| `/pause #123` 或 `暂停 #123` | 暂停当前 worker，保留分支和工作区 |
| `/resume #123` 或 `继续 #123` | 恢复暂停或等待中的 worker，重新排队 |
| `/retry #123` 或 `重试 #123` | 重试阻塞或失败的 worker |
| `/stop #123` 或 `停止 #123` | 结束 worker，释放并发名额 |
| `/fix #123` 或 `重新派发 #123` | 没有 worker 时重新排队；已有可恢复 worker 时恢复 |
| `/new` | 开启新话题，机器人会回复“已开启新会话”；切换话题时请在消息里写清新主题 |
| `/crash` | 管理员开启崩溃上报后，查看崩溃包的上传格式 |

群内命令建议带上 Issue 编号；不写编号时，机器人会尝试使用最近讨论的 Issue。控制动作会先检查当前状态，状态不允许时会直接回复当前状态，不会强行执行。

## GitHub Issue 评论区的命令

同一组命令也可以直接在 GitHub Issue 评论区使用，适合需要留下 Issue 评论记录的场景：

| 命令 | 作用 |
|---|---|
| `/status` | 查看当前任务状态、分支、PR 和最近错误 |
| `/pause` | 暂停当前任务 |
| `/resume` | 恢复暂停的任务 |
| `/retry` | 重试失败的任务 |
| `/stop` | 停止任务并释放并发名额 |
| `/fix` | 当前没有进行中的任务时，重新排队 |
| `/plan` | 在 `/plan` 后附上方案，登记一个方案版本 |
| `/approve vN` | 批准第 N 版方案；仅仓库 OWNER、MEMBER、COLLABORATOR 可执行 |

审批必须在 GitHub Issue 评论里完成。群里说“可以”“同意”“OK”不会被记录为审批，也不会触发批准流程。当前版本实现了 `/plan` 和 `/approve vN`；`/changes`、`/hold`、`/reject` 请先用普通评论说明，等待后续支持。

## 机器人会怎样回应

| 回复或现象 | 含义 | 你应该做什么 |
|---|---|---|
| 直接回答问题 | 这是一条问答，未进入建单流程 | 继续追问时把上下文补齐 |
| 追问缺少的信息 | 内容还不足以判断或复现 | 按它列出的问题一次答完 |
| 【待确认建单】DRAFT-xxxx | Issue 草稿已生成，尚未建单或派 worker | 核对标题和摘要，回复确认建单或取消建单 |
| 已确认并创建 Issue #N，并附链接 | 群内确认完成，已建单并进入修复队列 | 到 Issue 里补充细节，不要在群里重复发 |
| 这个问题已经有 Issue #N | 命中已有问题，新内容已追加 | 到该 Issue 继续讨论 |
| 已补充到 Issue #N | 内容已写入对应 Issue | 等待任务处理，必要时在 Issue 补充 |
| 没能确定要更新哪个 Issue | 消息里没有可识别的编号 | 带上 `#编号` 或 Issue 链接重发 |
| 处理失败，请稍后重试 | 模型、队列或上游服务临时异常 | 稍等后重试一次；持续失败请联系管理员 |

问答会尽快返回；复杂问题需要读代码，可能要几分钟。建单后的修复、验证和提 PR 受队列与仓库验证影响，不会在群里立即完成。任务卡住时，先在 Issue 里用 `/status` 查看状态，避免反复 @ 机器人。

## 这些事不要做

- 不要在群里粘贴密码、令牌、私钥、完整连接串或未脱敏的客户数据；
- 暂停、停止、重试会实际影响正在执行的任务，发送前确认 Issue 编号；
- 不要把多个无关问题塞进一条消息；
- 不要连续重复发送同一条消息，消息会按 ID 去重，重复发送不会加快处理；
- 不要让机器人绕过评审直接合并、访问其他仓库或执行破坏性操作；
- 不要把群聊里的“同意”当作审批，审批只认 GitHub Issue 里的 `/approve vN`；
- 不要把机器人的回答当作最终结论；涉及生产变更、数据修复和权限调整时，以代码、Issue 记录和人工评审为准。

## 给管理员的自检清单

群里长时间没有回应时，按顺序检查：

1. 配置台的“蓝信配置”里，机器人是否在线，群是否绑定到正确项目；
2. 项目是否配置了可用的 GitHub 凭据；
3. 消息是否 @ 了机器人，是否为文本或受支持的附件；
4. 配置台“最近消息”里是否有记录，状态是 `unbound`、`failed` 还是已建单；
5. `bot`、`scheduler`、`bridge` 三个服务是否健康，Webhook 是否正常投递。
6. 如需限制群内暂停、停止、重试的权限，需要在调度器增加身份白名单；当前版本按群成员身份执行。
7. Issue 正文显示“未知成员”时，检查蓝信应用是否有群成员/通讯录读取权限；机器人会按 `staffId` 查询真实姓名。

## 群公告版（可直接复制）

```text
【SmartPipe 蓝信机器人使用说明】

1. 在群里 @机器人 提问或反馈问题，未 @ 的消息不会处理。
2. 报缺陷请写清：版本/环境、复现步骤、实际结果、期望结果、影响范围、出现频率，附截图或脱敏日志。
3. 第一行写一句能当标题的话；一次只发一个主题。
4. 机器人判断为缺陷、明确需求或收到崩溃上报后，都会先在群里发待确认草稿；群成员回复“确认建单 DRAFT-xxxx”后才创建 GitHub Issue 并回链接，回复“取消建单”则不会建单。
5. 补充已有问题请写“@机器人 补充 #编号：……”，不要重复开新话题。
6. 群内可用 /new 开启新话题；/crash 仅在上传崩溃包时使用。
7. 群里和 GitHub Issue 评论区都支持 /status、/pause、/resume、/retry、/stop、/fix，建议带上 #编号；也可以直接说“暂停 #210”“继续 #210”。
8. 审批只认 GitHub Issue 里的 /approve vN，群里说“同意/OK”不算审批。
9. 不要发送密码、令牌、私钥和未脱敏的客户数据。
10. 确认建单后，修复需要排队和验证，不会立即完成；进展请看 Issue 和 PR。
```
