# 调度器工作流设计（草案，待确认）

日期：2026-11-09　状态：讨论稿

## 1. 目标

蓝信群里的一句话，最终变成一条可合并的 PR，全程不需要人手工搬上下文：

```
蓝信消息 → 意图判定 → GitHub Issue → 修复工作区 → 验证 → PR → 合并 → Issue 关闭
```

调度器负责"谁在什么时候处理哪条消息/哪个 Issue"，Codex 负责"怎么改代码"，现有
`patch-verifier` 负责"改得对不对"，admin-api 负责"能不能提交、能不能推"。

## 2. 角色划分

| 角色 | 数量 | 职责 | 权限边界 |
|---|---|---|---|
| bot ingress | 每机器人 1 个常驻 | WebSocket 收消息、验签、去重、群→项目绑定 | 只转发，不调模型 |
| scheduler | 1 个常驻 | 意图路由、Issue 建单与去重、队列、并发配额、worker 生命周期、GitHub 事件回流 | 持有调度库连接，不持 GitHub/蓝信明文 |
| chat worker | 按群/项目常驻（可复用线程） | 回答常规问题、结合项目代码定位问题、判断是否产品缺陷、输出结构化建单信息 | 只读沙箱，不能改代码、不能提交 |
| issue intake | scheduler 内逻辑 | 查重、待确认草稿、确认后建 Issue、回群链接、入队 | 经 admin-api 调 GitHub |
| fix worker | 每个活跃 Issue 1 个 | 改代码、自测、修复验证失败、响应 review 意见 | 只写自己的 worktree，不持 token |
| patch-verifier | 固定池 | 干净副本应用补丁、跑 smartpipe.yaml 必过命令 | 只读仓库 + 临时目录 |
| admin-api 门禁 | 现有 | `repo.commit` / `repo.push` / 建 PR / 审计 | 唯一接触 GitHub 凭据的服务 |

chat worker 和 fix worker 必须是两种权限：前者永远只读，后者只在
`/data/workspaces/<project>/issue-<n>` 内可写。

## 3. 消息处理流程

1. 群里 @机器人 的消息进入 bot，按 `msgId` 去重（现有 10 分钟窗口），按群找到项目绑定。
2. scheduler 把消息投给该群的 chat worker（同一群复用同一个 Codex thread，保留上下文）。
3. chat worker 输出三选一：
   - `answer`：普通问答、使用咨询、与产品无关 —— 直接回群，流程结束；
   - `issue`：可复现的缺陷/需求 —— 输出标题、摘要、复现步骤、影响范围、严重级别；
   - `need_info`：信息不足 —— 回群追问，消息挂起 24 小时，超时丢弃。
4. `issue` 进入建单确认：
   - 先查重（同项目内标题/错误签名相似度，或报错堆栈指纹）；
   - 命中已有 Issue：在该 Issue 追加评论（含新出现的群、用户、时间、原始消息），回群贴已有链接；
   - 未命中：持久化一份待确认草稿，把标题、级别、摘要和草稿编号发回群里；确认前不创建 Issue，也不派 worker；
   - 草稿生成后直接创建 Issue（标签 `from-lanxin` + `severity/*` + `source/<群名>`，正文带原始消息与截图）；建单失败时草稿保留，群成员回复 `确认建单 DRAFT-xxxx` 重试；
   - 回群贴 Issue 链接（引用确认消息），并把 `(project, issue)` 入队；`取消建单` 或 30 分钟过期则丢弃草稿。
   - 崩溃上报与 bridge 回退入口共用同一张草稿表和同一套确认命令；任何自动入口都不得直接建 Issue。崩溃草稿确认后还会回写 `crash_reports.issue_number/status`。
5. 入队是幂等的：`(project_id, issue_number)` 唯一，重复消息只会追加评论，不会产生第二个 worker。

### 3.1 全量观察与分级响应

bot 不再硬丢弃非 @ 群消息。启用 Scheduler 时，所有群消息都会写入会话历史（默认保留最近 20 条），并带上 `isAtMe` 与 `replyToBot`；调度器按群策略决定是否处理：

- `at_only`：仅处理 @、回复机器人或明确命令；
- `smart`：非 @ 消息先经过低成本的观察预筛，再输出 `silent / answer / triage` 和置信度；
- `all`：所有消息进入 agent，适合测试群。

影子模式下，非 @ 消息的判断和理由写入消息记录，但不回复、不建单。关闭影子后，普通回答受 `answer_confidence`、回复冷却和每群每小时限额约束；自动建单还需要 `auto_issue_enabled`、更高的 `auto_issue_confidence`、每日草稿限额，并且最终仍要群内确认。

副作用命令必须先通过入口保护：非 @ 的自然语言“暂停/恢复/重试/停止”不会执行，只接受 @ 机器人、回复机器人或明确的斜杠命令。多个机器人同时收到同一条消息时，通过 `scheduler_message_claims` 原子抢占，只有一个机器人继续处理。

## 4. 队列与并发

队列按「项目 → 优先级 → 入队时间」排序，用 `SELECT … FOR UPDATE SKIP LOCKED` 领取，保证多实例安全。

- 全局并发：默认 3 个 fix worker（可配 `SCHEDULER_MAX_FIX_WORKERS`）。
- 单项目并发：默认 2，防止一个仓库被占满。
- 单 Issue：永远最多 1 个 worker（数据库唯一约束兜底）。
- 验证并发：`patch-verifier` 默认 2 个槽位；验证排队不应占着 fix worker 的名额太久，可放宽到 4。
- 等待人工的 Issue 不占并发名额：worker 进入 `awaiting_review` 后注销为"挂起"，线程状态保留。

配额满时消息不丢：显示"排队第 N 位"，下一个 worker 空出来自动启动，并回群通知。

## 5. 仓库与工作区：共享镜像 + 每 Issue 一个 worktree

结论：**一个项目一份 canonical clone（bare 或普通镜像仓），每个 Issue fix worker 用独立 worktree。**

```bash
# 每个项目只做一次（或按需 fetch）
git clone --mirror <repo> /data/repos/<project>.git

# 每个 Issue
git -C /data/repos/<project>.git worktree add \
  /data/workspaces/<project>/issue-42 -b agent/issue-42 origin/main
```

理由：

- 仓库对象只存一份，几十个 Issue 并发也不会重复下载几百 MB；
- worktree 之间文件完全隔离，一个 worker 改坏不影响别人；
- 分支天然属于同一仓库，推 PR 不需要额外搬运；
- 清理只要 `git worktree remove --force`，不涉及对象回收。

代价与约束：

- 同一个分支不能同时检出两个 worktree；重试时用 `agent/issue-42-r2`，成功后清理旧分支；
- worktree 共享 refs，`fetch` 由 scheduler 串行执行，避免并发写锁冲突；
- `.git` 目录在容器重启后不会丢（挂载卷），但 worktree 元数据要能重建：启动时校验，缺失则重建。

不推荐"每个 Issue 完整 clone"：现在 `codex-pipeline` 就是这么做的，仓库稍大就会拖慢每个 Issue 的启动时间。

## 6. 一次 Issue 修复的完整步骤

1. **准备**：fetch 最新 `main`，创建 worktree 与 `agent/issue-<n>` 分支。
2. **读上下文**：Issue 正文 + 全部评论 + 关联截图；复杂 Issue 先走 `/plan` → 维护者 `/approve vN` 门禁（现有 `internal/gate`）。
3. **改代码**：Codex 在 worktree 内修改并自测，产出 unified diff。
4. **验证**：补丁交给 `patch-verifier`，在干净副本上应用并执行 `smartpipe.yaml` 的必过命令。
5. **提交推送**：验证通过后经 admin-api `repo.commit` + `repo.push` 推到 `agent/issue-<n>`。
6. **开 PR**：draft PR，标题 `fix: <issue 标题> (#<n>)`，正文含变更摘要、验证报告、`Fixes #<n>`。
7. **回写**：Issue 评论贴 PR 链接与验证结论；群里贴 PR 链接。
8. **响应反馈**：review 评论、CI 失败、冲突 → 唤醒同一个 worker（同一 worktree）继续改。
9. **合并**：PR 合并 → Issue 自动关闭 → worker 收尾。
10. **收尾**：删除 worktree，分支保留 7 天后清理，释放并发名额。

## 7. PR 策略

- 所有代码变更一律走 PR，禁止直接推 `main`。
- 分支命名 `agent/issue-<n>`，重试 `agent/issue-<n>-r<k>`。
- PR 从 draft 开始，验证通过后转 ready。
- 合并方式 squash，保持主干线性；PR 正文保留 `Fixes #<n>` 触发 Issue 自动关闭。
- 默认需要 1 个维护者 approve；可按项目开启"验证通过自动合并"（仍要求门禁全绿）。
- fix worker 没有合并权限，合并动作只能来自人工或 scheduler 的受控接口。

## 8. Worker 生命周期

一个 fix worker 的生命周期**绑定 Issue 的 open 状态**：

| 状态 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| `queued` | 等待名额 | 建单后 | 调度器领取 |
| `preparing` | 建 worktree、拉上下文 | 领取 | 准备完成 |
| `coding` | Codex 修改中 | worktree 就绪 | 产出 diff 或超时 |
| `verifying` | 干净副本验证 | 有 diff | 验证完成 |
| `pushing` | 提交、推送、开 PR | 验证通过 | PR 创建成功 |
| `awaiting_review` | 等人工/等 CI | PR 就绪 | review 通过/拒绝/超时 |
| `merged` | PR 已合并 | 合并事件 | Issue 关闭后清理 |
| `blocked` | 需要人工决策 | 重试超限、权限不足、需求不清 | 人工处理 |
| `closed` | Issue 已关闭，收尾 | Issue closed | worktree 清理完 |

关键规则：

- Issue 关闭（无论 PR 合并、人工关闭、重复合并）都会立刻终止对应 worker，取消进行中的 turn。
- 关闭后再有消息：不新建 worker；在 Issue 里评论（若已 reopen 则重新入队）。
- 蓝信与 Issue 是同一会话的两端：群消息转成 Issue 评论，Issue 评论摘要回群，避免两边各说各话。

## 9. 多轮人工交互（复杂 Issue）

复杂 Issue 很少一轮能改完。交互必须做成"回合制"，而不是让 worker 一直跑、人一直在旁边看。

### 9.1 唯一会话：Issue 是事实源，蓝信是远端窗口

- 人在群里 @机器人 或引用原消息回复 → bridge 把消息落成一条 Issue 评论（带 `来源：蓝信/群名/发言人/msgId`）。
- 人在 GitHub 直接评论 Issue/PR → 同样进入同一会话。
- worker 每轮输出写一条 Issue 评论，并把摘要同步回群（附链接，不刷屏）。
- 这样多轮对话天然有完整时间线、审计和上下文，worker 永远读得到全量历史。

### 9.2 三条唤醒通道，一个 worker

| 来源 | 触发 | 处理 |
|---|---|---|
| 蓝信群消息 | @机器人 或引用 bot 的消息 | bridge → scheduler → 找到该 Issue 的活跃 worker |
| Issue 评论 | 任何人评论（含 `/` 命令） | webhook → scheduler |
| PR review 评论 | review / 行内评论 | webhook → scheduler |

三条通道都唤醒**同一个 Codex thread、同一个 worktree**，保证上下文连续。只有 Issue 关闭才销毁。

### 9.3 状态机增加两个状态

- `awaiting_input`：worker 已给出问题，等人工回答。worktree 与 thread 保留，**不占并发名额**。
- `paused`：人工 `/pause`，冻结当前轮，恢复需 `/resume`。

每轮结束 worker 必须产出三件事，否则视为本轮未完成：本轮做了什么、验证结果、下一步需要谁提供什么。

### 9.4 每轮上下文如何组装

resume 时不重放全部历史，而是拼一份"回合包"：

1. Issue 正文 + 方案版本（若有 `/approve vN`）；
2. 评论摘要（截至上一轮的结论、决定、否决项）+ 最近 10 条原文；
3. 当前分支与最近一次提交、PR diff 摘要；
4. 上一轮验证失败日志（如有）；
5. 本轮新增的人工输入（结构化解析后的答案）。

Codex 侧复用同一个 app-server thread 连续 `turn`，长对话定期生成"阶段小结"评论并折叠旧上下文。

### 9.5 提问协议：一次问清，避免乒乓

worker 提问必须结构化，一条评论里最多 3 个问题，每个问题给选项或默认值：

```markdown
<!-- smartpipe:question id=Q3 round=4 -->
需要你确认 2 件事：
1. 兼容旧客户端吗？ A) 必须兼容（默认） B) 可以升级
2. 灰度范围？ A) 全量 B) 先 10% 群
@需要回答的人
```

- 人可以直接在群里回 `1A 2B`，也可以在 Issue 里自由文本回答。
- chat 层把回答解析成结构化答案回贴 Issue，worker 下一轮直接消费。
- 回答含糊时 worker 只追问一次；仍不清楚就按"默认值 + 明确假设"继续，并在评论里写清假设，避免无限循环。

### 9.6 权限：补充信息 vs 拍板

- 任何群成员都可以补充信息、复现步骤、日志。
- 方案方向、取舍、超出范围的改动，只有**维护者 / 项目 owner / Issue 发起人**可以拍板。
- 多个答案冲突时，以维护者为准，并把"决定 + 理由"写进评论，后续轮次以此为准。
- 现有的 `/plan` → `/approve vN` 就是这条规则的特例：方案版本一旦批准，worker 不得擅自偏离，偏离必须重新走审批。

### 9.7 轮次与成本控制

- 单 Issue 人工轮次上限默认 10 轮；每轮 token 预算独立计算。
- 24 小时无回复：提醒一次；48 小时无回复：转 `paused` 并在群里说明"等待谁提供什么"。
- 连续 3 轮没有实质进展（无代码变更、无新结论）：转 `blocked`，升级给 owner，附当前最佳方案、阻塞点和建议决策。
- 自动修复（验证失败）不计入人工轮次，但同一失败原因重试 3 次仍失败才算需要人工。

### 9.8 典型的多轮场景

| 场景 | 交互形态 |
|---|---|
| 需求不清楚 | worker 列 2–3 个问题 → 人回答 → worker 出方案 → `/approve` → 开工 |
| 方案讨论 | worker 只出方案和影响面，不动代码；批准后才进 `coding` |
| 验证失败 | 自动带日志重试，不找人；连续失败才回群求助 |
| PR review | 每条 review 评论是一轮输入；worker 追加 commit 到同一分支，不重开 PR |
| 需求变更 | Issue 评论里改需求 → worker 重估；范围变化大则关旧 PR、按新方案重开 |
| 人工直接改分支 | worker 下一轮先 fetch + rebase，人工提交优先，不覆盖 |
| 长时间挂起 | worktree 落盘快照（分支 + patch）后回收，恢复时从分支重建 |

### 9.9 幂等与防重复

- 蓝信 `msgId` ↔ Issue 评论 `comment_id` 双向映射，同一条消息只落一次评论、只回一次群。
- worker 回群用 Issue 评论链接作为引用，群里看到的每条通知都能点回原文。
- 群里只同步"摘要 + 链接"，完整过程留在 Issue，避免刷屏和双份维护。

## 10. 失败、重试与人工介入

- 单轮 Codex 超时 30 分钟；同一 Issue 最多 3 轮自动重试，指数退避（1/5/15 分钟）。
- 验证失败：把失败日志回贴 Issue，让同一 worker 带日志再改一轮（这是最有效的自愈路径）。
- 合并冲突：自动 rebase 到最新 main 并重跑验证，连续 2 次冲突转 `blocked`。
- 重试超限、权限不足、需求不明确：标 `blocked`，群里 @发起人，评论里写清楚缺什么。
- 命令（群里或 Issue 评论均可）：`/pause`、`/resume`、`/retry`、`/stop`、`/status`、`/fix`。
- 所有命令先落到 Issue 评论（可追溯），再由 scheduler 执行。

## 11. 数据与接口（建议）

```sql
work_queue(id, project_id, issue_number, priority, state, attempts,
           last_error, source_chat_id, source_msg_id, created_at, updated_at)
-- unique(project_id, issue_number) where state in ('queued','running','blocked')

workers(id, queue_id, project_id, issue_number, state, branch, worktree,
        thread_id, pr_number, model, started_at, heartbeat_at, budget_tokens)

chat_threads(chat_id, project_id, thread_id, last_message_at)

issue_links(project_id, issue_number, chat_id, msg_id, pr_number, created_at)
```

调度器对外只开放内网接口：收消息、收 GitHub 事件、查询队列/worker、执行命令。
GitHub webhook 继续由 bridge 接收，转成 `issue_comment` / `issues` / `pull_request` 事件投给 scheduler。

## 12. 可观测性

- 看板：队列长度、平均等待、活跃 worker、成功率、平均修复时长、token 成本。
- 每个 Issue 一条时间线：建单 → 排队 → 领取 → 每轮 Codex → 每次验证 → PR → 合并。
- 告警：worker 心跳丢失、排队超过 30 分钟、PR 超过 3 天未合并、单 Issue 成本超阈值。

## 13. 待拍板的三件事

1. **并发上限**：全局 3 / 单项目 2 是否合适？服务器现在只有一个 patch-verifier 容器，验证并发要先定。
2. **合并权限**：PR 必须人工 approve 后合并，还是允许按项目开启"验证通过自动合并"？
3. **建单确认**：chat worker 判定是产品缺陷后，先在群里发结构化草稿；群成员明确确认后才建 Issue 和派 worker。

## 14. 分阶段落地

- P0：scheduler 骨架 + 队列表 + worktree 管理 + 单 Issue 全链路（建单 → 修复 → 验证 → PR）。
- P1：chat worker 常驻与去重、蓝信回链、Issue 评论回流、并发配额。
- P2：自动 rebase、成本预算、看板、命令体系。
- P3：多仓库项目、截图/日志附件转 Issue、按项目策略（自动合并/人工审批）。

## 15. 实现状态（2026-11-09）

已落地：

- `backend/internal/scheduler`：调度器核心（队列、并发配额、chat/fix 两种 worker、Issue 事件回流、命令）。
- `backend/cmd/scheduler`：常驻服务，内网端口 8098，接口
  `/internal/scheduler/messages`、`/internal/scheduler/github`、`/internal/scheduler/workers`。
- 蓝信入口：bot 配置 `SCHEDULER_URL` 后把归一化消息交给调度器；未配置时仍可回退 bridge。
- GitHub 回流：bridge 把 `issue_comment` / `issues` 事件转发给调度器（`SMARTPIPE_SCHEDULER_URL`）。
- 门禁：调度器不持 GitHub 凭据，建单/评论/搜索/PR 走 admin-api；提交与推送走 `repo.commit`/`repo.push`。
- 存储：`scheduler_workers`（同时是队列）、`scheduler_links`（消息幂等）、`scheduler_chat`（会话上下文）、`scheduler_issue_drafts`（待确认草稿）、`scheduler_message_claims`（多机器人抢占）、`scheduler_chat_replies`（回复限流），当前迁移版本 34。
- 角色提示词：`ChatSystemPrompt`（只读、JSON 输出）与 `FixSystemPrompt`（只改 worktree、不提交）在
  `backend/internal/scheduler/prompts.go`。

与设计稿的偏差（有意为之）：

1. Codex thread 没有跨轮复用：SDK 当前以 ephemeral thread 运行，改为每轮重新组装"回合包"
   （Issue + 最近评论 + 本轮输入 + 上轮验证日志）。对用户体验一致，且避免长会话上下文漂移。
2. 去重先用 GitHub 搜索做标题精确匹配；错误指纹相似度列为后续增强。
3. PR 固定 draft 创建，合并仍需人工；自动合并留给项目策略开关。
4. 机器人评论过滤：调度器自己发的评论带 `<!-- smartpipe:bot -->`，作者以 `[bot]` 结尾的评论一律忽略。

补充的闭环能力（2026-11-09 第二版）：

- Issue 上的人工评论会同步回发起群（作者 + 摘要 + 链接），群里始终看得到进展。
- 群消息引用 Issue（`#12`）且没有活跃 worker 时，会建 worker 入队，而不是只留一条评论。
- 每 5 分钟对账一次：Issue 已关闭但 worker 还挂着（webhook 丢失/重启）时自动收尾并回收 worktree。
- 每轮追加提交都会回群提示 PR 更新，关闭时回群带 PR 编号与链接。
- 群响应策略：`at_only / smart / all`、影子模式、非 @ 消息轻量观察（silent/answer/triage）、回答/建单置信度阈值、冷却与每小时限额、自动建单每日限额；副作用命令入口保护。
